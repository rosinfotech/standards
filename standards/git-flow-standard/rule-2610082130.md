# The Rosinfotech Base Standards

## The Git Flow Standard

### Variants

#### Rule #2610082130

* Context:

  * A team with release discipline - promotions are versioned wholes, several releases may be in flight at once;

* Description:

  * release/x.y is based on main and lives on the stage environment - the train;

  * A task branch forks from the current release/x.y per [Rule #2610082116](/standards/git-flow-standard/rule-2610082116.md);

  * Each task merges into dev freely and opens a merge request into release/x.y;

  * release/x.y merges into main via a merge request as a whole release;

  * Several release branches may ride in parallel - the release train;

  * A task slipping to the next train moves by cherry-pick or a repeated merge request;

  * Stabilization commits of release/x.y flow back: main -> dev after the release, or a direct sync into dev for a long train;

  * main syncs into dev after every release per [Rule #2610082118](/standards/git-flow-standard/rule-2610082118.md);

  * Parallel tasks run in git worktrees - one worktree per task in flight;

  * A hotfix follows [Rule #2610082120](/standards/git-flow-standard/rule-2610082120.md) - delivery via main, propagation back into the active train and dev;

  * The versioning - version-per-release: release/x.y carries the version, entering main stamps x.y.0, a hotfix stamps x.y.z+1 per [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md); the assembly commit lands on release/x.y before the release merge, the tag lands on main per [Rule #2610092126](/standards/git-flow-standard/rule-2610092126.md); the fragments accumulate in the train per [Rule #2610092124](/standards/git-flow-standard/rule-2610092124.md);

  * The environments:

    * dev deploys to the dev environment;

    * release/x.y deploys to the stage environment;

    * main deploys to production;

  * The deviations from the canon (nvie):

    * the release branch is assembled by task merge requests, not cut from dev as a snapshot;

    * merge requests act as gates - the classic model has none;

    * the fork base is the release branch, not dev;

* Scheme:

  ```mermaid
  flowchart LR
      T["branch-task<br>(fork: release/x.y)"] -->|"merge"| D["dev"]
      T -->|"MR"| R["release/x.y"]
      R -->|"MR"| M["main"]
      M -->|"sync"| D
      D --> DE[("dev environment")]
      R --> SE[("stage environment")]
      M --> PE[("prod")]
  ```

* Benefits:

  * A release is a reviewable whole - the promotion merge request shows exactly what production receives;

  * Parallel trains allow a hot line and a feature line at once;

  * The stage environment always shows a candidate release, never an accidental mix;

* Examples:

  * Case #1:

    * Incorrect:

      * tasks merged straight into main "to ship faster" - the next release merge request shows an unreviewable diff;

    * Correct:

      * tasks ride the release/x.y train and main receives only whole, stabilized releases.
