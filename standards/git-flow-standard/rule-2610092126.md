# The Rosinfotech Base Standards

## The Reviewed Merge to Release to Main Flow Standard

### Versioning

#### Rule #2610092126

* Context:

  * The commit history carries the fixed message structure `<version>: <Type>: <message>` - a stamp commit with a free-form message breaks the reading habit and any tooling over the log;

* Description:

  * The stamp / assembly commit message follows the structure:

    * `$NEXT: <Type>: <main message>` - the version first, then the type and the main message of the assembled section;

    * `<Type>` and the main message come from the most significant fragment - the one placed first in the assembled section;

  * Merge commits carry no version prefix - they are entry points, not release acts:

    * a task merge-request merge: `Merge pull request #N` / `Merge branch 'branch-task'`;

    * a promotion or release merge: `Merge branch 'staging'` / `Merge pull request #N (release x.y.0)`;

  * A task enters main as one commit - the squash discipline:

    * variant #2: the free merge is a squash (`git merge --squash`) carrying the senior fragment message - `<Type>: <message>` without a version; the stamp commit that follows carries the version (the same rhythm as #3);

    * variants #4-#5: the promotion merge request enables squash (GitHub "Squash and merge", the GitLab squash option); its title carries no version - the senior fragment message or the promotion name - and the version arrives with the stamp commit that follows on main (the same rhythm as #3);

    * variant #3: the merge request enables squash; its title carries no version (the version is born at the entry per [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md)) - the version arrives with the stamp commit that follows;

    * the task branch commits themselves follow `<Type>: <message>` (no version prefix) - the branch reads by the same convention as the history;

  * A tag never travels without its commit: the tag push joins its commit's push - one atomic push of the branch and the tag, never a bare `--tags` broadcast nor a tag pointing at an unpushed commit;

  * Variant #1 stays on the makefile flow: `make git_flow_commit_push "<Type>: <message>"` - the version prefix and the tag are added by the framework automatically;

* Benefits:

  * The whole history - stamps, merges and tags - reads by one convention;

  * The main message of the section and the commit message can never diverge - they share the source fragment;

* Examples:

  * Case #1 - the stamp message:

    * Incorrect:

      * `Release: v0.5.2` - no version-first structure, the type is not a CHANGELOG subsection;

    * Correct:

      * `0.5.2: Added: The payment retry policy` - the version, the type, the main message of the section;

  * Case #2 - the merge message:

    * Incorrect:

      * `0.5.2: Merge branch 'branch-task'` - a merge commit must not carry a version prefix;

    * Correct:

      * `Merge branch 'branch-task'` - the version arrives with the stamp commit that follows.
