# The Rosinfotech Base Standards

## The Git Flow Standard

### Common invariants

#### Rule #2610082120

* Context:

  * Production is broken and the clock is running; the environment queue (staging, release/x.y) promotes wholesale - a hotfix riding the queue would either wait for the batch or drag unreviewed neighbors into production;

* Description:

  * The delivery:

    * the hotfix branch forks from main and targets main via a merge request - bypassing the queue;

    * pre-production verification deploys the hotfix branch itself to the stage environment (a CI branch deploy), not a merge into the queue;

  * The propagation - the back-merge, immediately after the merge into main:

    * main -> staging (variant #4) or main -> release/x.y (variant #5, when the train is active);

    * main -> dev - the standing sync of [Rule #2610082118](/standards/git-flow-standard/rule-2610082118.md);

  * The propagation is mandatory, not optional hygiene:

    * staging and release/x.y are fork bases per [Rule #2610082116](/standards/git-flow-standard/rule-2610082116.md) - without the fix, new tasks build against the bug;

    * the stage environment keeps reproducing the bug - false reports from QA and clients;

  * A bug found in unsold code - on stage, in the queue, in an active release - is not a hotfix: it is a regular task into the current gate;

  * Variant #3 has no separate hotfix concept - no queue exists, the fix is a regular task through the main gate;

* Scheme:

  ```mermaid
  flowchart LR
      H["hotfix<br>(fork: main)"] -->|"MR"| M["main"]
      M --> PE[("prod")]
      M -->|"sync"| Q["staging / release/x.y"]
      M -->|"sync"| D["dev"]
  ```

* Benefits:

  * Production gets the fix at merge-request speed, without waiting for a batch;

  * The queue stays clean - unreviewed neighbors never ride a hotfix into production;

  * The fix cannot be lost - every live branch receives it via the back-merge;

* Examples:

  * Case #1:

    * Incorrect:

      * a payment bug hotfix merged into staging and waiting three days for the next promotion;

    * Correct:

      * the hotfix goes main via a merge request, then main is back-merged into staging and dev.
