# The Rosinfotech Base Standards

## The Git Flow Standard

### Versioning

#### Rule #2610092124

* Context:

  * A shared CHANGELOG.md is a conflict hotspot - every task writes to the same top of the file, and the gate turns into a merge-resolution exercise;

* Description:

  * A task branch carries its change record as a fragment:

    * the path: `changelog-fragments/<UTLBL>.<type>.md` in the repository root;

    * `<UTLBL>` - the task timestamp label; `<type>` - one of added, changed, fixed, deprecated, removed, security (exactly the CHANGELOG subsections);

    * the content: one English line without the leading `- ` - the stamp assembles the section from fragments;

  * The fragment lifecycle:

    * created in the task worktree together with the work;

    * rides the merge request into the gate;

    * consumed by the stamp: the CHANGELOG section is assembled, the fragment file is deleted;

    * the free merge into dev carries a fragment copy - the standing main -> dev sync carries the removal;

    * no task branch forks from dev, so a consumed fragment cannot be assembled twice;

  * Variant #1 has no fragments - there are no task branches; the solo actor writes the CHANGELOG section in the commit itself;

* Benefits:

  * Zero conflicts on CHANGELOG.md - each task writes its own file;

  * The section assembles mechanically - grouping by the `<type>` extension;

  * The dev integration line never breaks the record - copies arrive and leave with the merges;

* Examples:

  * Case #1:

    * Incorrect:

      * the task branch edits the top of CHANGELOG.md - three concurrent tasks meet in a three-way conflict at the gate;

    * Correct:

      * each task adds `changelog-fragments/2610091815.added.md` with one line - the stamp assembles them into one section.
