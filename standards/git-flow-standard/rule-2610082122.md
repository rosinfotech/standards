# The Rosinfotech Base Standards

## The Git Flow Standard

### Variants

#### Rule #2610082122

* Context:

  * One developer, one task in focus - any branch or merge-request ceremony carries no value, it only slows the single actor down;

* Description:

  * Commits land directly in main - there are no branches, no merge requests, no dev line;

  * main deploys to production;

  * The versioning - version-per-merge: every commit stamps the next tag per [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md); the message and the tag come from the makefile flow per [Rule #2610092126](/standards/git-flow-standard/rule-2610092126.md); there are no fragments - the CHANGELOG section is written in the commit itself per [Rule #2610092124](/standards/git-flow-standard/rule-2610092124.md);

  * The canonical name is trunk-based development - the solo mode of the published model (trunkbaseddevelopment.com);

* Scheme:

  ```mermaid
  flowchart LR
      W["working copy"] -->|"commit"| M["main"]
      M --> PE[("prod")]
  ```

* Benefits:

  * Zero ceremony - the entire budget goes into the task;

  * A linear history - no merge commits to read around;

  * The feedback loop is one commit long;

* Examples:

  * Case #1:

    * Incorrect:

      * a solo repository running branch-per-fix with self-approved merge requests;

    * Correct:

      * direct commits into main with CI green on every commit.
