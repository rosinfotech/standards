# The Rosinfotech Base Standards

## The Reviewed Merge to Release to Main Flow Standard

### Variants

#### Rule #2610082126

* Context:

  * Many tasks and many people - integration must stay cheap while the release line becomes guarded;

* Description:

  * A task branch forks from main per [Rule #2610082116](/standards/git-flow-standard/rule-2610082116.md);

  * Each task merges into develop freely - integration without a gate;

  * Each task opens a merge request into main - the gate;

  * main syncs into develop after every merge into main per [Rule #2610082118](/standards/git-flow-standard/rule-2610082118.md);

  * Parallel tasks run in git worktrees - one worktree per task in flight;

  * The versioning - version-per-merge: the release actor stamps on main right after the merge-request merge per [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md); the task carries its fragment per [Rule #2610092124](/standards/git-flow-standard/rule-2610092124.md); the standing main -> develop sync carries the fragment removal; the stamp message per [Rule #2610092126](/standards/git-flow-standard/rule-2610092126.md);

  * The environments:

    * develop deploys to the develop environment;

    * main deploys to production;

  * There is no separate hotfix concept - a production fix is a regular task through the same gate;

  * The deviations from the canon:

    * Lite = Reviewed Merge to Release to Main Flow without release branches;

    * the classic lite promotes develop batches into main - here per-task merge requests with the fork from main;

* Scheme:

  ```mermaid
  flowchart LR
      T["branch-task<br>(fork: main)"] -->|"free merge"| D["develop"]
      T -->|"MR (squash)<br>+ fragment"| M["main"]
      M --> S["seal: assemble,<br>stamp + tag"]
      M -->|"sync"| D
      D --> DE[("develop environment")]
      M --> PE[("prod")]
  ```

* Benefits:

  * Integration stays free - develop absorbs everything immediately;

  * main carries only reviewed tasks - the gate is per task, not per batch;

  * develop remains disposable - it can be reset from main at any moment;

* Examples:

  * Case #1:

    * Incorrect:

      * a task branch forked from develop - its merge request into main carries the neighbors' half-finished work;

    * Correct:

      * the task forks from main, merges into develop for integration only, and its merge request into main shows the task alone.
