# The Rosinfotech Base Standards

## The Reviewed Merge to Release to Main Flow Standard

### Variants

#### Rule #2610082128

* Context:

  * A team that must verify acceptance on a production-like stage before promotion - a defect caught on stage is cheaper than one caught in production;

* Description:

  * A task branch forks from staging per [Rule #2610082116](/standards/git-flow-standard/rule-2610082116.md) - the task develops against the neighbors it will ride the promotion with;

  * Each task merges into develop freely - integration without a gate;

  * Each task opens a merge request into staging - the acceptance gate;

  * staging merges into main via a merge request as needed - the promotion is wholesale and is itself the gate;

  * main syncs into develop after every promotion per [Rule #2610082118](/standards/git-flow-standard/rule-2610082118.md);

  * Parallel tasks run in git worktrees - one worktree per task in flight;

  * A hotfix follows [Rule #2610082120](/standards/git-flow-standard/rule-2610082120.md) - delivery via main, propagation back into staging and develop;

  * The versioning - version-per-merge (per promotion): the fragments accumulate in staging unconsumed and ride the promotion merge request into main per [Rule #2610092124](/standards/git-flow-standard/rule-2610092124.md); the seal assembles the CHANGELOG section on main right after the promotion, lands the stamp commit with the tag and syncs the gates per [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md); the stamp message per [Rule #2610092126](/standards/git-flow-standard/rule-2610092126.md);

  * The environments:

    * develop deploys to the develop environment;

    * staging deploys to the stage environment;

    * main deploys to production;

  * The deviations from the canon:

    * the canonical GitLab Flow directs main downstream into the environment branches - here the direction is inverted: staging is the acceptance queue and main receives promoted batches;

    * Lite = one environment branch instead of the staging-plus-production pair;

* Scheme:

  ```mermaid
  flowchart LR
      T["branch-task<br>(fork: staging)"] -->|"free merge"| D["develop"]
      T -->|"MR (squash)<br>fragment rides"| S1["staging"]
      S1 -->|"promotion MR (squash)<br>fragments ride unconsumed"| M["main"]
      M --> S2["seal: assemble,<br>stamp + tag"]
      S2 -->|"sync / reset"| D
      S2 -->|"sync / reset"| S1
      D --> DE[("develop environment")]
      S1 --> SE[("stage environment")]
      M --> PE[("prod")]
  ```

* Benefits:

  * Every promotion to production has been verified on a production-like environment;

  * The stage environment is the accepted set by construction - staging branch and stage environment never disagree;

  * The fork from staging makes integration surprises local to development, not gate discoveries;

* Examples:

  * Case #1:

    * Incorrect:

      * a task forked from main and merged into staging - on stage it breaks against a neighbor it never saw in development;

    * Correct:

      * the task forks from staging, the neighbor is present from the first commit.
