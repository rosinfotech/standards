# The Rosinfotech Base Standards

## The Git Flow Standard

### Common invariants

#### Rule #2610082116

* Context:

  * A task branch forked from dev drags all accumulated work-in-progress into its merge request - the gate stops reviewing the task and starts reviewing the dirt;

  * A task branch forked blindly from main hides an integration surprise behind the gate - the task will be tested and released next to already accepted neighbors it has never seen;

* Description:

  * A task branch forks from its merge-request target:

    * variant #3 - from main;

    * variant #4 - from staging;

    * variant #5 - from the current release/x.y;

  * The fork base therefore matches the environment the task will actually join - the gated neighbors are present during development, and the merge-request diff contains only the task itself;

  * The dirt classification:

    * gated dirt - staging and release/x.y: everything there passed a merge request and rides to main with the next promotion - a legal fork base;

    * ungated dirt - dev: arbitrary work-in-progress with no obligations - the only forbidden fork base;

  * The exception - a task knowingly depending on someone's unmerged work:

    * fork from that task branch or from dev, and state the dependency in the merge request;

    * or wait for the predecessor to land and fork from the target afterwards;

* Benefits:

  * Every merge request reviews exactly one task;

  * Integration conflicts surface during development, not behind the gate;

  * dev stays what it is meant to be - a sink, never a source;

* Examples:

  * Case #1:

    * Incorrect:

      * variant #4, a task forked from dev - the merge request into staging carries three half-finished neighbor tasks;

    * Correct:

      * the task forks from staging and develops against the neighbors it will ride the promotion with.
