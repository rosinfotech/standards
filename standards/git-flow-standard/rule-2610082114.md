# The Rosinfotech Base Standards

## The Git Flow Standard

### The ladder

#### Rule #2610082114

* Context:

  * A repository needs a different flow at different team sizes and release discipline - without named variants every project re-invents and re-argues the model from scratch;

  * The variant names must point at recognizable industry canons, so a discussion starts from published material instead of private diagrams;

* Description:

  * The standard defines five flow variants:

    * #1 Trunk-Based Development - commits go directly into main;

    * #2 GitHub Flow - a task branch merges into main without a merge request;

    * #3 Git Flow Lite - dev integration plus a merge-request gate on main;

    * #4 GitLab Flow Lite - the staging branch between the task merge request and main;

    * #5 Git Flow - the release branch as the vehicle into main;

  * The applicability ladder:

    * #1 - one developer, one task in focus;

    * #2 - solo work or a circle of fully trusted peers, many sequential tasks;

    * #3 - many tasks and many people, cheap integration, guarded release line;

    * #4 - a team that must verify acceptance on a production-like stage before promotion;

    * #5 - a team with release discipline - versioned trains promoted as wholes;

  * The variants #3-#5 differ in exactly one dimension - what stands between the task merge request and main:

    * #3 - nothing;

    * #4 - the staging branch;

    * #5 - the release/x.y branch;

  * The comparison table:

    | # | Name | Fork point | MR target | Between MR and main | Hotfix |
    |---|------|------------|-----------|---------------------|--------|
    | 1 | Trunk-Based Development | - | - | - | regular commit |
    | 2 | GitHub Flow | main | - | - | regular branch |
    | 3 | Git Flow Lite | main | main | - | regular task |
    | 4 | GitLab Flow Lite | staging | staging | staging | via main |
    | 5 | Git Flow | release/x.y | release/x.y | release/x.y | via main |

  * The naming provenance:

    * #1, #2, #5 - canonical industry names (trunkbaseddevelopment.com, GitHub Flow, the nvie branching model);

    * #3, #4 - derived names: "Lite" marks the trimmed canon, and every deviation from the canon is listed in the variant rule;

* Benefits:

  * The team picks a variant by two questions - how many people and how many gates stand between a commit and production;

  * The names are googlable - the canon behind each variant is published material;

  * The ladder grows one step at a time - a team migrates #2 -> #3 -> #4 -> #5 without re-learning the whole model;

* Examples:

  * Case #1 - choosing by the ladder:

    * Incorrect:

      * a solo project running a five-branch release ceremony because "that is how Git Flow looks";

    * Correct:

      * a solo project runs variant #1 or #2 and migrates only when people and gates appear;

  * Case #2 - naming a custom mix:

    * Incorrect:

      * a model with dev, staging and per-task merge requests silently called "Git Flow";

    * Correct:

      * the deviations from the canon are listed in the variant rule, so the name carries no false expectations.
