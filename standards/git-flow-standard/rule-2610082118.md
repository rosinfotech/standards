# The Rosinfotech Base Standards

## The Reviewed Merge to Release to Main Flow Standard

### Common invariants

#### Rule #2610082118

* Context:

  * main accumulates merge commits no other branch carries - merge-request merges and promotions; without synchronization the histories diverge though the content matches, and the next merge arrives as noise;

* Description:

  * The task flow is one-directional - toward main:

    * a task branch merges into develop freely - integration without a gate;

    * a task branch enters its gate - staging, release/x.y or main - via a merge request;

    * develop is a dead end: its inputs are task merges and syncs from main, its outputs are none;

    * promotion never sources from develop - main is fed by the gates only (task merge requests in #3, staging promotions in #4, release wholes in #5);

  * The sync discipline:

    * main -> develop after every promotion into main - a one-time hygiene operation, not a pipeline step;

    * main -> staging / release/x.y after a hotfix - the back-merge of [Rule #2610082120](/standards/git-flow-standard/rule-2610082120.md);

    * a gate branch whose content is fully promoted may be reset to main instead of merged - the tooling resets such gates during the seal (develop stays disposable, staging and the trains converge);

    * stabilization commits of a long-lived release/x.y may sync into develop directly, without waiting for the release to land;

* Benefits:

  * The histories converge - the next promotion is a clean merge, not a conflict excavation;

  * Every branch has exactly one defined upstream, so the diagram never grows cycles;

  * develop keeps its single role - the integration sink;

* Examples:

  * Case #1:

    * Incorrect:

      * a promotion into main leaves develop without the merge commits - two weeks later the promotion merge request shows a wall of phantom conflicts;

    * Correct:

      * main is synced into develop right after every promotion - the histories stay convergent.
