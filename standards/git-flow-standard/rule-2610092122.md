# The Rosinfotech Base Standards

## The Reviewed Merge to Release to Main Flow Standard

### Versioning

#### Rule #2610092122

* Context:

  * A version read from a file (.version, CHANGELOG.md) before the entry into main races with a concurrent entry - two actors read the same last version and both prepare the same next one;

  * A merged file gives no guarantee against duplicates - the last writer wins silently or the merge conflicts; the version must be assigned where it becomes true - on main;

* Description:

  * The version truth is the tag on main: the last stamped version is read as `git describe --tags --abbrev=0` on the main tip - never from `.version` or CHANGELOG.md;

  * The intended bump is declared in `.version` line 2 (the version-update contract: line 1 is the current committed version, line 2 is the future version - the declaration point; `version_update` copies line 2 into line 1 and substitutes the listed files):

    * a declared line 2 (a valid semver above the last tag) is stamped as is - the bump granularity is the actor's choice, one declaration point;

    * the steady state (line 2 equal to the last tag on main - nothing declared) means the default increment - the patch bump of the tag;

    * a declared version below the tag-derived minimum (the patch bump of the tag) is an incompatibility: the stamp refuses with an `Error` instead of silently stamping a duplicate or a lower version;

  * `.version` is therefore both the intent input (line 2) and the regenerated artifact of the stamp (after the stamp both lines hold the stamped version); CHANGELOG.md is a generated artifact of the stamp;

  * The version granularity:

    * variants #1-#4 - version-per-merge: every entry into main stamps the next version;

    * variant #5 - version-per-release: the release/x.y train is the version - entering main stamps x.y.0, a hotfix stamps x.y.z+1;

  * The deferral (variants #1-#3): the release actor confirms every tagging - a deferral performs no version act (in #1 the commit carries no version prefix, in #2-#3 the fragments accumulate on main) and the next confirmed stamp versions the accumulated work as one; the tooling gates every tagging with a confirmation defaulting to deferral (a tag may trigger the deployment pipeline) (a flag answers it for agents) - tagging is always an explicit act; a routine pattern of deferrals is a ladder signal to move to #4;

  * The version event is the entry into main - the last gate:

    * #1 - every commit of the solo actor;

    * #2 - the merge of the task branch into main;

    * #3 - the merge-request merge into main;

    * #4 - the staging promotion - one version collects all fragments accumulated in staging;

    * #5 - the release merge into main;

  * The stamp protocol - the release actor (a human or an agent) at the last gate:

    ```mermaid
    flowchart TD
        A["release actor (human / agent)<br>prepares the entry into main"] --> B["rebase the entry on the main tip"]
        B --> C["read the last version: tag on main<br>git describe --tags --abbrev=0"]
        C --> D["resolve the next semver<br>the .version intent when declared and valid,<br>otherwise the patch bump of the tag"]
        D --> E["assemble the CHANGELOG section from fragments,<br>regenerate the .version artifact"]
        E --> F["merge into main, push tag vNext"]
        F --> G{"tag rejected: duplicate?"}
        G -->|"yes: someone stamped first"| C
        G -->|"no"| H["main carries vNext, fragments consumed"]
    ```

  * The duplicate guarantee:

    * the tag is pushed together with the branch in one atomic push - `git push --atomic origin main "$NEXT"` - and the server rejects a duplicate tag;

    * on rejection the actor re-reads the tag, recomputes and re-stamps - a retry loop instead of a silent duplicate;

  * The assembly location:

    * #1 - the commit is the stamp;

    * #2-#3 - the stamp is a commit on main right after the entry (the #2 squash entry or the #3 merge-request merge);

    * #4-#5 - the assembly (the CHANGELOG section, the fragment removal, `.version`) is a commit in the gate branch (staging / release/x.y) before the promotion - main never sees raw fragments and the gate branch stays clean after the promotion;

  * The makefile flow migration: the stamp reads the tag as the floor and `.version` line 2 as the declared intent - the two are reconciled at every stamp, an incompatible declaration blocks;

* Benefits:

  * No duplicate versions - the tag ref is atomic and server-rejected on collision;

  * The history reads linearly - every entry into main carries a version and a tag;

  * The bump granularity is the actor's choice, declared in one place and validated against the tag floor - a stale declaration can never ship a lower version;

  * Concurrent entries converge mechanically - rejection and recompute instead of a silent overwrite;

* Examples:

  * Case #1:

    * Incorrect:

      * two release actors both read `.version` = 0.5.1, both stamp 0.5.2 - the second push silently overwrites the first;

    * Correct:

      * both read the tag on the main tip after rebase; the second `git push --atomic origin main 0.5.2` is rejected, the actor recomputes 0.5.3 and re-stamps.
