# The Rosinfotech Base Standards

## The Git Flow Standard

### The repository marker

#### Rule #2610092156

* Context:

  * A repository working by one of the five variants must declare it machine-readably - otherwise agents and newcomers guess the flow from the commit history and guess wrong;

* Description:

  * A repository declares its variant by a root marker file - committed, copied as-is from the standard's assets;

  * The five marker names (exhaustive - no other variants exist) - the prefix mirrors the standard's URL origin: `github.com/rosinfotech` -> `github-com-rosinfotech`:

    * `.github-com-rosinfotech-trunk-based-development` - the asset [.github-com-rosinfotech-trunk-based-development](/standards/git-flow-standard/assets/.github-com-rosinfotech-trunk-based-development);

    * `.github-com-rosinfotech-github-flow` - the asset [.github-com-rosinfotech-github-flow](/standards/git-flow-standard/assets/.github-com-rosinfotech-github-flow);

    * `.github-com-rosinfotech-git-flow-lite` - the asset [.github-com-rosinfotech-git-flow-lite](/standards/git-flow-standard/assets/.github-com-rosinfotech-git-flow-lite);

    * `.github-com-rosinfotech-gitlab-flow-lite` - the asset [.github-com-rosinfotech-gitlab-flow-lite](/standards/git-flow-standard/assets/.github-com-rosinfotech-gitlab-flow-lite);

    * `.github-com-rosinfotech-git-flow` - the asset [.github-com-rosinfotech-git-flow](/standards/git-flow-standard/assets/.github-com-rosinfotech-git-flow);

  * The marker content - the declaration, the standard link and the rules list:

    * `Flow: Variant #<N> - <Name>` - the variant of the repository;

    * `Standard: https://github.com/rosinfotech/standards#the-git-flow-standard` - the link to the standard;

    * `Rules:` followed by one URL per line - every rule of the standard that governs the variant, no others;

  * The rules list per variant:

    * #1 - the variant rule [Rule #2610082122](/standards/git-flow-standard/rule-2610082122.md); the versioning rules [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md) and [Rule #2610092126](/standards/git-flow-standard/rule-2610092126.md) - no fork point, no sync, no hotfix, no fragments: the variant has no branches, no gates, no queue;

    * #2 - the variant rule [Rule #2610082124](/standards/git-flow-standard/rule-2610082124.md); the versioning rules [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md), [Rule #2610092124](/standards/git-flow-standard/rule-2610092124.md), [Rule #2610092126](/standards/git-flow-standard/rule-2610092126.md);

    * #3 - the variant rule [Rule #2610082126](/standards/git-flow-standard/rule-2610082126.md); the fork point [Rule #2610082116](/standards/git-flow-standard/rule-2610082116.md); the directions and sync [Rule #2610082118](/standards/git-flow-standard/rule-2610082118.md); the versioning rules [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md), [Rule #2610092124](/standards/git-flow-standard/rule-2610092124.md), [Rule #2610092126](/standards/git-flow-standard/rule-2610092126.md) - no hotfix rule: the variant has no queue;

    * #4 - the variant rule [Rule #2610082128](/standards/git-flow-standard/rule-2610082128.md); the fork point [Rule #2610082116](/standards/git-flow-standard/rule-2610082116.md); the directions and sync [Rule #2610082118](/standards/git-flow-standard/rule-2610082118.md); the hotfix [Rule #2610082120](/standards/git-flow-standard/rule-2610082120.md); the versioning rules [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md), [Rule #2610092124](/standards/git-flow-standard/rule-2610092124.md), [Rule #2610092126](/standards/git-flow-standard/rule-2610092126.md);

    * #5 - the variant rule [Rule #2610082130](/standards/git-flow-standard/rule-2610082130.md); the fork point [Rule #2610082116](/standards/git-flow-standard/rule-2610082116.md); the directions and sync [Rule #2610082118](/standards/git-flow-standard/rule-2610082118.md); the hotfix [Rule #2610082120](/standards/git-flow-standard/rule-2610082120.md); the versioning rules [Rule #2610092122](/standards/git-flow-standard/rule-2610092122.md), [Rule #2610092124](/standards/git-flow-standard/rule-2610092124.md), [Rule #2610092126](/standards/git-flow-standard/rule-2610092126.md);

  * The markers are pointer assets per the exception of [Rule #2609271055](/standards/documentation-standard/rule-2609271055.md) - they declare and reference, they inline no norms;

  * Exactly one marker per repository - more than one is a violation, detected by globbing `.github-com-rosinfotech-*` in the root;

  * The lifecycle:

    * created when the variant is chosen - scaffolded at project initialization alongside `.editorconfig`;

    * updated by the very commit that migrates the repository to another variant - a migration without the marker update is a divergence;

    * audited first: the declared variant is checked against the actual branch structure - a divergence is an audit finding;

  * Agents read the marker as the input - the flow is never guessed from the commit history;

* Benefits:

  * The variant is visible in `ls` and machine-readable in one glob - no history archaeology;

  * Agents, CI and newcomers share one declaration source;

  * A stale marker is detectable mechanically - the audit compares the declaration with the branch structure;

* Examples:

  * Case #1:

    * Incorrect:

      * the root carries `.github-com-rosinfotech-gitlab-flow-lite` while merges go straight into main without any gate - the declaration diverged from reality;

    * Correct:

      * the marker matches the actual variant, and the migration commit that moves the team to another variant replaces the marker file in the same commit.
