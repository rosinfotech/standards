# The Rosinfotech Base Standards

## The AI Standard

### AGENTS.md

#### Rule #2609262010

* Context:

  * AI coding agents (Claude Code, Codex and others) load instruction files named `AGENTS.md` from several locations: the user-global agent config, the repository root and subdirectories; without a fixed model the files drift and agents miss critical prohibitions.

* Description:

  * The company AGENTS.md model is a composition - the behavioral core plus the role assets included on demand:

    * The BASE AGENTS.md - the behavioral core (three sections), identical everywhere; the composition is fixed by [Rule #2609271528](/standards/ai-standard/rule-2609271528.md); the source of truth is the asset [AGENTS-STANDARD-BASE.md](/standards/ai-standard/assets/AGENTS-STANDARD-BASE.md);

    * The role assets - the role scope and the role toolchain, composed into an AGENTS.md as marked blocks on demand; two kinds:

      * the functional roles: Harness, Git Manager, Technical Writer, Researcher;

      * the engineering roles: architect, backend engineer, frontend engineer;

      * each role asset is fixed by its rule in this subsection and has its ready-to-copy asset in the standards repository;

  * The composition precedence: the BASE core is never overridden - an included role block never weakens the core sections of the composed file;

  * The role assets are independent of each other: several may be composed into one AGENTS.md (e.g. a backend role together with a frontend role) - the roles do not share state and never contradict each other;

  * Rule inclusion: abstract norms live in the standards catalog (The Rosinfotech Base Standards); an AGENTS.md file is a composition - it inlines the agent-relevant text of the rules it includes with their full meaning, not references (an agent can not follow external links and must not be tempted to fetch or analyze them); rule IDs and links appear only where the file needs them on purpose - e.g. the lint config repositories an agent applies in repositories; the catalog is the single source of truth - when a catalog rule changes, the AGENTS.md assets are updated from it;

  * The BASE AGENTS.md supports marked inclusions of the role assets from the standards repository: the link base refreshes, the closest-by-meaning asset is selected and fetched on the user's command ([Rule #2610031427](/standards/ai-standard/rule-2610031427.md)) - the composition becomes operable in place, without manual editing;

  * The self-update: on the user's request to update the AGENTS.md itself ("обнови AGENTS.md", "update your AGENTS.md") the agent refreshes everything the file takes from the standards repository:

    * the core zone - everything from the file start to the first inclusion marker, or the whole file when no inclusions exist - is replaced with the current BASE asset fetched from the repository;

    * every marked inclusion block is re-fetched from its URL (the update path of [Rule #2610031427](/standards/ai-standard/rule-2610031427.md));

    * the content that is neither the core zone nor a marked block stays untouched;

    * the base core is recognized by the `# Global rules (all projects)` heading - a file without it is reported and left as is;

  * Placement: the user-global agent config on the engineer's machine and/or the repository root;

  * Project-specific knowledge (commands, stack, architecture) is not carried by AGENTS.md files - the agent reads it from the repository itself: the Makefile, package.json and the build config.

* Benefits:

  * Uniformity - predictable agent behavior everywhere;

  * No duplication - shared rules are written once and updated in one place;

  * Safety - critical prohibitions (git, secrets) can not be weakened by an included role block.

* Examples:

  * Case #1 - conflict resolution:

    * Incorrect:

      * an included role block says "commit after successful tests" and the agent commits;

    * Correct:

      * the core section says git writes require an explicit order - the core wins in the composed file, no commit happens without it;

  * Case #2 - project knowledge:

    * the agent needs the test command - it reads the Makefile / package.json of the repository, not an AGENTS.md file;

  * Case #3 - self-update:

    * the user: "обнови AGENTS.md";

    * the agent fetches the current BASE asset, replaces its core zone, re-fetches every marked block from its URL - and leaves any custom content between the blocks untouched.
